For a verified existing PR, the actual PR number may be supplied to `gh pr edit` (example: `bash ./scripts/commit-feature.sh && gh pr edit 2181 --body-file .git/AI_PR_BODY_CUSTOM.md`). Keep the exact existing command sequence, scripts, hooks and custom-body filename; do not hardcode the example number. The script commits, pushes and opens/updates **one** PR to `dev`; the `gh` step replaces the generic PR body. Verify authenticated CLI, branch freshness, intended diff, required files, local checks and actual PR-body update. Reuse the same PR for review corrections. **Bounded autonomous CI correction is the default.** After verified publication, Codex may monitor required CI on the current PR head and correct failures attributable to its assigned changes on the same branch/PR, with at most three autonomous remote CI correction cycles per task; stop earlier if the same failure persists after two attempts, the cause is unclear, the fix requires scope expansion, or a material blocker needs owner input. Reproduce failures with targeted local tests first whenever feasible; use remote Linux integration for genuinely environment-specific failures that cannot be reproduced locally. Do not repeatedly push speculative fixes or wait on superseded CI runs. For material implementation/review defects, demonstrate a targeted regression failing before the fix and passing afterward; if not feasible, report the exact limitation and equivalent evidence. Never weaken tests, skip required checks, bypass safeguards, merge or deploy. The owner may explicitly select immediate-return mode (report after publication without monitoring) or local-only mode. Report promptly at green exact-head CI or the stop condition: PR URL, final pushed SHA, targeted local results/limitations, CI results/status, correction cycle count and any unresolved blockers. CI performs full-suite validation by default; do not claim pending or unavailable checks passed. No owner publication handoff is required. Diagnose partial publication before retrying, and stop for material blockers without bypassing safeguards, force-pushing, merging or deploying. Explicit local-only owner instructions override this default.
5. Review the **actual GitHub PR diff through the GitHub connector**, not only Codex summaries, local diffs, or test reports. Start independent review as soon as a published head is available, in parallel with CI where feasible; coordinate corrections to avoid concurrent conflicting edits, and re-review any amended head. Inspect risk paths and missing regression cases; post actionable findings on the **same PR** and send corrections without waiting for superseded CI runs. Re-review amended commits. Never require the user to paste lengthy diffs.
6. Confirm what merged, then reconcile roadmap milestones through an appropriate docs PR.

### Existing feature branch freshness exception

The requirement for a new feature branch remains strict: `scripts/start-feature.sh` fetches `origin/dev`, fast-forwards local `dev`, verifies that local `dev` exactly equals `origin/dev`, and only then creates the branch. Existing feature branches may be stale only for the narrow backlog case below:

- The tracked `.githooks/pre-commit` hook fetches `origin/dev` and finds the unique merge-base with the current branch.
- If the branch is behind, it enumerates every commit reachable in `merge-base..origin/dev`—including older merged side branches and merge commits—and compares each commit against every parent. Every changed path must be exactly `docs/feature-backlog.md`.
- Mixed changes, any other documentation or repository path, reverted code, missing objects, fetch failures, non-unique history, and any other ambiguity block the commit. Commit messages, PR labels, and tags are never evidence for this exception.
- While completing a merge, the hook permits only a single merge head equal to the current `origin/dev`; this prevents the guard from blocking the legitimate synchronization merge itself. Git-generated messages for that verified merge are accepted, while ordinary commits remain subject to Conventional Commit enforcement.
- Fresh clones and existing clones use the same tracked executable hooks through `scripts/install-git-hooks.sh`; `start-feature.sh` and `commit-feature.sh` install them automatically. The installer is idempotent for `.githooks`, but refuses to overwrite an effective custom `core.hooksPath` or active legacy `.git/hooks/*` files. An existing clone must review/diff those local hooks and explicitly set `git config --local core.hooksPath .githooks` before migration; unrelated safeguards are never silently discarded.

## 3. Validation: fast and proportional

- For a **new database migration**, validate on a safe representative **existing-schema** database before any production release. ### Windows SSH passphrase and agent recovery (validated November 17, 2026)

- An already-open interactive droplet shell does **not** establish that a new SSH session can authenticate. `Permission denied (publickey)` does not by itself prove that the key is missing or invalid. A batch-mode SSH client cannot prompt to unlock a passphrase-protected identity.
- For the existing operator-managed Windows `clash-vm` SSH alias, first check the effective identity selection and the **public fingerprint only**, not private-key contents. The November 17 incident found that the offered ED25519 public key matched an existing `tilo` authorized key; the server accepted the public key, but new batch-mode logins failed because no usable agent could provide the unlocked private key. An interactive login succeeded after the operator entered the passphrase locally. Distinguish key acceptance from successful signing/authentication.
- Windows OpenSSH `ssh-agent` was initially **stopped and disabled**. On the operator's own Windows workstation, the authorized recovery was: inspect `sc query ssh-agent`; if needed, have the operator change its startup type to manual with `sc config ssh-agent start= demand` in an administrator CMD; start it with `sc start ssh-agent`; load the **existing** passphrase-protected identity with `ssh-add "C:\Projects\droplet_clashcookies"` and enter the passphrase locally; then test `ssh -o BatchMode=yes -o ConnectTimeout=10 clash-vm "whoami"` from ordinary CMD. The final probe returned `tilo`, and Codex separately confirmed that its execution environment could authenticate. **Do not print, store, remove, or change the passphrase, private key, authorized keys, or VM SSH policy for diagnosis.**
- `ssh-agent` state and loaded identities are **not durable assumptions** across reboots, Windows user contexts, isolated Codex environments, or new sessions. Recheck the actual SSH capability rather than claiming retained access. An authorized operator may unload the key after work with `ssh-add -d "C:\Projects\droplet_clashcookies"`; do not unload it unexpectedly during active authorized work.
- These commands are **Windows CMD**, not remote Linux commands. Do not paste Windows paths into an existing `tilo@...` shell. If the normal agent workflow fails, stop and report the blocker; do not add keys to the VM, try alternate identities or elevate remote privileges without separate approval. The incident evidence and delivery-specific scope remain in [the November 17 discovery preflight](diagnostics/production-vm-discovery-operator-preflight-2026-11-17.md).
