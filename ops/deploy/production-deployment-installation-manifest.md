## Installation prerequisites

Before activation, independently verify and record:

1. The deployment operator identity and effective UID/GID/group/capability permissions. For the credential boundary, independently verify `credentialAccess.strategy=operator-owned-immutable-read-only`: both credential files are owned by the non-root operator with exact mode `0600`, have the filesystem immutable flag set, sit below a root-owned non-writable parent, and the operator has no `sudo`, `docker` group, rootful Docker socket, `CAP_LINUX_IMMUTABLE`, or equivalent authority. This proves the existing process can read the files but cannot clear, replace, or modify them. Also prove the operator cannot modify the executor, helper, lock parents, manifest, or release record.
2. The actual production checkout, Docker/network/port topology, active runtime name and labels, candidate-worktree location, and startup artifact.
3. That the application startup path cannot apply Prisma migrations implicitly; only the reviewed migration runner may request production migration.
4. The protected credential source and the credential-access boundary above, database identity, migration-capable privilege boundary, baseline migration state, backup/restore evidence, disk capacity, health monitoring, and recovery authority. The runtime database role's effective grants must be verified with approved read-only database evidence; the manifest username alone does not prove those grants or prove that the role cannot migrate.
5. Exact installed artifact hashes, owner/group/mode, canonical parent paths, lock ownership, release-record append-only control, and the activation authorization digest. Confirm the artifact manifest and promoted SHA remain unchanged after build and before stopping the existing runtime.

## One-time installation procedure

1. Review the offline diff, focused tests, full CI evidence, and this manifest. Approve exact paths, identities, modes, hashes, operator, recovery authority, and handoff conditions.
2. Revalidate the existing VM facts read-only. Do not read the existing application `.env`; provision separate `0600` migration and least-privileged runtime environment sources through the approved secret-delivery process. Set each credential file's owner to the non-root deployment operator, set mode `0600`, set the filesystem immutable flag (`chattr +i` on the verified Linux filesystem), and keep the parent root-owned and non-writable. Configure the operator's Docker access as rootless; do not add `docker`-group membership or a rootful Docker socket, and do not grant `sudo`/capability access that can clear the immutable flag.
3. Install the immutable entrypoint/module bundle, helper, manifest, lock directories, credential sources, release-record target, and promoted-artifact root only at separately approved paths. Record the exact credential owner/mode/immutable/parent and effective operator/Docker evidence in the installation handoff. Leave `/home/tilo/deploy-prod.sh` unchanged.
4. Re-read every installed artifact with no-follow identity checks and compare the approved hashes/metadata. Confirm the new entrypoint fails closed when activation, identity, lock, credential, module bundle, artifact root, or preflight evidence is absent.
5. Run one separately approved non-migration rehearsal. Confirm one runtime launches the verified per-release artifact with the least-privileged runtime environment, health/revision verification succeeds, and candidate cleanup does not remove the launched artifact; validate release-record handling separately on the migration-aware path.
6. After startup-migration separation and migration preflight are independently approved, run one approved migration-bearing release through the production environment gate. Do not retry an ambiguous migration; retain the recovery-required state.
7. Only after successful handoff, rollback rehearsal, and owner confirmation may a separate change make the legacy command an argument-free `exec` handoff. This implementation does not replace or modify it.

No step above is an instruction to perform production work in this repository task. Installation, rehearsal, handoff, rollback, migration, and release approval remain separate authorized actions.
